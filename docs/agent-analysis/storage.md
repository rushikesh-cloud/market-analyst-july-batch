# Analysis evidence and artifact storage

Evidence source metadata, supporting excerpts, and retrieval provenance are copied
into `analysis_evidence`. They do not depend on the original document remaining
available. IDs are generated by the server and are local to a run. Re-registering
identical evidence preserves the first entry and retrieval timestamp. A later run
gets an independent ID and provenance. Models cannot update registered snapshots.
Terminal publication compares each cited snapshot against the registered content,
not just its ID, and checks that chart/data artifact IDs belong to the same run.

Artifact bytes live in `analysis-artifacts/<run-id>/attempt-<lease-generation>/`
under the repository by default. Set `ANALYSIS_ARTIFACT_DIR` to choose another
absolute storage root. The directory is ignored by Git. The API and analysis
worker must share the same durable filesystem volume and configured root. Keep
this volume across application restarts and releases; include it with PostgreSQL
in backups. Completed artifacts are retained for historical results. No Docker
build or deployment is required to configure this storage contract.

Writes use server-generated UUID filenames, a private temporary file, file and
directory synchronization, and an atomic rename before metadata registration.
Publication locks the run and checks the worker owner, generation, and unexpired
lease. An expired worker cannot register its file or replace a later attempt's
file. Failed registration removes the unregistered file; an abrupt process death
may leave an unregistered orphan, which the API never serves. No automatic
history or orphan deletion runs in this version.

Artifact reads resolve only registered metadata for the requested run. Directory
and file descriptors reject symlinks, registered paths must match the generated
run/attempt/ID layout, and bytes must match their saved size and SHA-256. Missing
files report `artifact_unavailable`; changed bytes report `artifact_corrupt`.
Public metadata includes MIME type, byte size, digest, and purpose, never the
filesystem path. Use restrictive filesystem access for the API/worker service;
only those processes should write this volume.

Run the storage tests with synthetic evidence and isolated PostgreSQL schemas:

```bash
ANALYSIS_TEST_POSTGRES=1 uv --directory backend run --env-file ../.env python -m unittest tests.test_analysis_storage -v
```

The normal application PostgreSQL configuration is used only to create and remove
a randomly named test schema. Existing application rows are never test fixtures.
